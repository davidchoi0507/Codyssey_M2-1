## 2. 핵심 결정과 이유

### ① 곡 분석 = librosa(측정) + Gemini(듣기) 혼합
- **librosa**는 BPM·에너지·구간을 매번 같은 값으로 잰다 → 숫자와 하이라이트 시점의 근거
- **Gemini**는 오디오를 직접 듣고 감정 흐름·악기·보컬을 말로 풀어 준다 → 해석
- 숫자를 같이 주면 LLM이 지어내지 못하고, LLM이 숫자에 의미를 붙인다.
- 실제로 같은 곡을 두 번 들려줬을 때 Gemini가 짚은 클라이맥스가 20초가량 달랐다 → **시점은 librosa가 정하고 Gemini는 후보 중에서 고르기만** 한다.
- 버린 대안: faster-whisper + CLAP(정해 둔 라벨 점수만 나옴), 수치 + 텍스트 LLM만(곡을 듣지 않음)

### ② 듣기 모델 = Gemini
- 음악 오디오 이해가 되는 API. Claude API는 오디오 입력이 없고, OpenAI 오디오 모델은 음성 대화용이라 음악 이해는 검증이 안 됨.
- **Gemini 2.5 Flash는 쓰지 않음**: 종료 단계(구글 클라우드 종료일이 제출일 10/20과 같음).
- 무료 티어는 모델별 하루 20회 → 같은 키로 **모델 폴백**(3.8 → 3.7 → …)과 예비 키로 해결, 비용 0원.

### ③ 글·이미지 = 코디세이 API
- 과정에서 제공하는 키라 팀 비용·키 관리가 하나로 모임.
- **DALL-E 3는 쓰지 않음**: 2026-05-12 API 종료.
- 코디세이 프록시가 JSON 모드·도구 호출을 지원하지 않아(400) **프롬프트 JSON + 파서**로 받고, 측정값은 LLM이 다시 쓰지 않고 코드가 붙인다.
- 키 2개를 번갈아 쓰고, 한 키가 막히면(429 등) 다음 키로 넘어간다.

### ④ 에이전트 = LangChain, "해석 먼저 → 사람이 확인 → 생성"
- 해외 비슷한 서비스는 분석을 숨기고 결과만 낸다. 우리는 **A&R 노트를 먼저 보여 주고 사람이 고치거나 수락**하게 했다.
- 수락한 노트 하나를 비주얼·카피·피칭 에이전트가 함께 써서 결과물 톤이 맞는다. 세 에이전트는 병렬로 돈다.

### ⑤ 서버 = Oracle Cloud VM 한 대
- 메모리 24GB, ARM 4코어. 분석·영상 처리에 충분하다.
- API·분석·파일이 한 자리에 있어 결과물을 서버 사이에서 옮기지 않는다.
- 버린 대안: Render(무료 티어는 잠들고 디스크가 사라짐), Supabase(서비스를 더 늘릴 필요 없음)

### ⑥ DB = SQLite, 작업 대기열 = FastAPI 비동기 + 프로세스 풀
- 4주 프로젝트 규모에는 SQLite(WAL)로 충분하고 운영이 단순하다.
- Celery·Redis 없이 상태를 DB에 둬서 서버가 다시 켜져도 작업을 이어 간다.

### ⑦ Mock 모드 없음
- 처음부터 실제 API로 만들어 결과물 품질을 바로 확인했다. 비용은 하루 생성 횟수 제한으로 관리.

### ⑧ n8n(노코드 자동화) 미사용
- 업로드 → 분석 → 생성 → 렌더링 → 검사가 **단계마다 결과를 저장하고 실패한 단계부터 다시** 해야 해서, 서버 한 곳에서 Python으로 직접 관리하는 쪽이 단순했다.
- 자동화가 필요한 부분(매일 보관 삭제, 신고 알림, 테스트 요약)도 Python 스크립트·텔레그램으로 처리.

### ⑨ RAG 대신 코드 규칙
- 유통사 규격(커버 크기, 제목 표기, 등록 마감일 등)은 **틀리면 반려**라 정확해야 한다. 문서를 검색해 LLM이 판단하게 하지 않고, 조사한 규격을 코드 규칙으로 넣어 검사한다.

### ⑩ 개인정보·보관 최소화
- 서비스 종료일(2026-10-31)에 음원·공개 곡·계정·설문을 일괄 삭제. 로그인은 닉네임·고유 식별값만.
- 듣는 사람은 로그인 없이 반응할 수 있게 해서 문턱을 낮췄다.
